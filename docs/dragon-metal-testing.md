# Dragon / Olala 7A1B on Apple Metal: build & test checklist

The Metal kernels for `GGML_OP_MAMBA3_MIMO` and `GGML_OP_GEODESIC`
(`ggml/src/ggml-metal/kernels/mamba3.metal`) were written on Linux without a Metal
compiler. They passed a clang syntax/address-space check and a functional emulation
against the CPU reference, and were first validated on real hardware in PR #1
(Apple M5 Pro, macOS 26.4.1: op tests 18/18, CPU-vs-Metal greedy identical, pp512 ≈ 2070 t/s,
tg128 ≈ 70 t/s). On a different chip or macOS version, run the steps below in order and
send back the outputs listed in section 6 if anything differs.

Model used below: `olala-dpo99k-bf16.gguf` (use **bf16** on the GPU, see section 5).

## 1. Build

```sh
cmake -B build -DGGML_METAL=ON -DCMAKE_BUILD_TYPE=Release -DLLAMA_CURL=OFF
cmake --build build -j --target test-backend-ops llama-completion llama-bench
```

`GGML_METAL_EMBED_LIBRARY` is on by default, so the `.metal` sources are compiled
**when the Metal backend initializes** (at program start), not by cmake. A shader
compile error shows up at startup as

```
ggml_metal_library_compile_all: failed to build 'mamba3' library: <compiler errors>
```

and the Metal backend is then unavailable.

## 2. Shader compile check (fast, gives line numbers)

Compile the generated, self-contained source of the new kernel file offline:

```sh
xcrun -sdk macosx metal -c build/ggml/src/ggml-metal/autogenerated/ggml-metal-embed-mamba3.metal \
    -o /tmp/mamba3.air 2>&1 | tee /tmp/mamba3-metal-compile.txt
```

No output = OK. (If that file does not exist, configure with
`-DGGML_METAL_EMBED_LIBRARY=OFF` and the build itself runs `xcrun metal` on each kernel
file; errors then appear in the build log.)

## 3. Op tests (Metal vs CPU)

```sh
./build/bin/test-backend-ops -b MTL0 -o MAMBA3_MIMO              2>&1 | tee /tmp/t-mamba3.txt
./build/bin/test-backend-ops -b MTL0 -o MAMBA3_MIMO_CACHE_FUSION 2>&1 | tee /tmp/t-mamba3-fusion.txt
./build/bin/test-backend-ops -b MTL0 -o GEODESIC                 2>&1 | tee /tmp/t-geodesic.txt
```

(`-b MTL0` restricts the run to the first Metal device; the backend names are printed at
the start of every run.) Expected:
10/10 `MAMBA3_MIMO`, 4/4 `MAMBA3_MIMO_CACHE_FUSION`, 4/4 `GEODESIC` OK. The cases
cover decode (T = 1), batched decode, short prefill (serial kernel, T < 64), chunked
prefill (T >= 64, incl. a partial tail chunk and multi-sequence), the register-state
fast path (Dragon dims 128/4/64) and the generic path (other dims), and the
MAMBA3_MIMO + CPY cache fusion.

If `MAMBA3_MIMO_CACHE_FUSION` fails while `MAMBA3_MIMO` passes, rerun it with
`GGML_METAL_FUSION_DISABLE=1`: if it then passes, the bug is in the fused state write.

Per-op timings (useful for tuning):

```sh
./build/bin/test-backend-ops perf -b MTL0 -o MAMBA3_MIMO,GEODESIC 2>&1 | tee /tmp/perf-ops.txt
```

Optional broader check of the other ops the Dragon graph uses (takes several minutes):

```sh
./build/bin/test-backend-ops -b MTL0 -o MUL_MAT,MUL_MAT_ID,FLASH_ATTN_EXT,ARGSORT,GET_ROWS,SET_ROWS,L2_NORM,RMS_NORM,CONCAT 2>&1 | tail -5
```

## 4. Full model

Greedy completion, CPU reference vs Metal. `DRAGON_PORTABLE=1` makes the CPU run use the
exact graph the GPU runs (verified on Linux: token-identical to the default CPU graph for
this prompt):

```sh
M=olala-dpo99k-bf16.gguf
P="The history of the Roman Empire is a long and complex story that begins with"

# CPU reference (no GPU device at all)
DRAGON_PORTABLE=1 ./build/bin/llama-completion -m $M --device none -p "$P" -n 64 --temp 0 --seed 1 \
    -no-cnv -fa 1 -fit off -c 4096 --no-display-prompt > /tmp/cpu.txt

# Metal, everything offloaded; GGML_METAL_FUSION_DEBUG=1 prints fusion counts at exit
GGML_METAL_FUSION_DEBUG=1 ./build/bin/llama-completion -m $M -ngl 99 -p "$P" -n 64 --temp 0 --seed 1 \
    -no-cnv -fa 1 -fit off -c 4096 --no-display-prompt -v > /tmp/metal.txt 2> /tmp/metal.log

diff /tmp/cpu.txt /tmp/metal.txt && echo IDENTICAL
grep -E "splits|MAMBA3|fusion|error|unsupported" /tmp/metal.log
```

The prompt above is 15 tokens, so it exercises the serial (short-ubatch) M kernel. Repeat
with a long prompt (>= 64 tokens) for the chunked prefill path:

```sh
python3 -c "print('In 1820 the town council met to discuss the new bridge. ' * 30)" > /tmp/long.txt
DRAGON_PORTABLE=1 ./build/bin/llama-completion -m $M --device none -f /tmp/long.txt -n 64 --temp 0 --seed 1 \
    -no-cnv -fa 1 -fit off -c 4096 --no-display-prompt > /tmp/cpu-long.txt
./build/bin/llama-completion -m $M -ngl 99 -f /tmp/long.txt -n 64 --temp 0 --seed 1 \
    -no-cnv -fa 1 -fit off -c 4096 --no-display-prompt > /tmp/metal-long.txt
diff /tmp/cpu-long.txt /tmp/metal-long.txt && echo IDENTICAL
```

What to look for:

- `sched_reserve: graph (pp bs=512, tg bs=1): nodes = ..., splits = A / B` in
  `/tmp/metal.log`: A and B should be small (1-3). A large value (~30 or more) means some
  op fell back to the CPU; rerun with `GGML_SCHED_DEBUG=1` to see which op.
- With `GGML_METAL_FUSION_DEBUG=1` the exit stats should list `MAMBA3_MIMO+CPY` (29 per
  graph evaluation: one per M layer).
- Greedy output identical (or diverging only late, after many tokens, on near-ties).
  An early divergence or garbage means a kernel bug; send the files from section 6.

Benchmarks:

```sh
./build/bin/llama-bench -m $M -ngl 99 -p 512 -n 128 -fa 1 | tee /tmp/bench.txt
./build/bin/llama-bench -m $M -ngl 99 -p 512 -n 128 -fa 1 -ub 2048 -b 2048 | tee -a /tmp/bench.txt
```

## 5. Notes

- bf16 weights need `has_bfloat` on the device (Metal 3.1, i.e. recent macOS). On
  M1/M2, bf16 is supported but not native in hardware, so bf16 matmuls are slower
  than on M3/M4.
- Quantized GGUFs: decode matmuls (mat-vec) keep f32 activations; prefill matmuls
  (mat-mat, > 8 tokens) convert the activations to **f16** for K-quants/q8_0, so
  activations above 65504 would overflow. Dragon has large outlier activations (the
  same root cause as the CUDA quant failures); if quantized models produce garbage on
  long prompts but not on short ones, that is the likely cause, not the new kernels.
  Test bf16 first.
- Kill switches: `GGML_METAL_FUSION_DISABLE=1` (all fusions, incl. MAMBA3_MIMO + CPY),
  `GGML_METAL_CONCURRENCY_DISABLE=1` (serializes dispatches; if this fixes a failure
  it points at a missing barrier/hazard).

## 6. What to send back

1. `/tmp/mamba3-metal-compile.txt` (section 2), or the full startup log if the backend
   failed to initialize.
2. `/tmp/t-mamba3.txt`, `/tmp/t-mamba3-fusion.txt`, `/tmp/t-geodesic.txt`; for a failing
   test, also rerun it with `GGML_METAL_FUSION_DISABLE=1` and with
   `GGML_METAL_CONCURRENCY_DISABLE=1` and send those outputs.
3. `/tmp/cpu.txt`, `/tmp/metal.txt`, `/tmp/metal.log`, `/tmp/cpu-long.txt`,
   `/tmp/metal-long.txt`.
4. `/tmp/bench.txt` and `/tmp/perf-ops.txt`, plus the chip (`sysctl -n machdep.cpu.brand_string`)
   and macOS version (`sw_vers`).
